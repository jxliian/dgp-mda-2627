## 3. Puntos Tratados y Discusión

- **Punto 1: Revisión de historias de usuario.**  
  Se revisó la forma correcta de redactar historias de usuario siguiendo la estructura:  
  **“Como [rol] quiero [característica/objetivo] para [valor o beneficio]”.**  
  Se comprobó la necesidad de que cada historia represente una funcionalidad concreta y aporte un beneficio identificable para el usuario.

- **Punto 2: Pruebas de aceptación.**  
  Se trabajó en la definición de pruebas de aceptación para las historias de mayor prioridad, utilizando escenarios que contemplan tanto el funcionamiento correcto como situaciones de error o casos alternativos.

- **Punto 3: División de historias en tareas.**  
  Se acordó descomponer las historias de usuario principales en tareas de desarrollo más pequeñas, incluyendo diseño de interfaz, validación de datos, implementación, gestión de errores y pruebas.

- **Punto 4: Priorización de requisitos.**  
  Se estudió y aplicó el método **MoSCoW** como mecanismo para establecer la importancia relativa de las historias de usuario:
  - **Must:** funcionalidades imprescindibles.
  - **Should:** funcionalidades importantes pero no críticas.
  - **Could:** funcionalidades deseables.
  - **Would:** funcionalidades que pueden posponerse a futuras versiones.

- **Punto 5: Representación visual de prioridades.**  
  Se decidió que la prioridad de las historias se reflejará también visualmente en la documentación mediante diferentes colores en las cabeceras de las tablas, manteniendo además la prioridad escrita para no depender únicamente del color.

- **Punto 6: Documentación en LaTeX.**  
  Se revisó el formato de presentación de las historias de usuario. Las historias principales incluirán nombre de usuario, historia, prioridad, pruebas de aceptación y tareas, mientras que las historias secundarias podrán utilizar una tabla reducida.

- **Punto 7: Coherencia de la documentación.**  
  Se detectó la importancia de revisar que todas las historias incluidas en cada ejercicio o documento pertenezcan al sistema correspondiente y evitar reutilizar por error historias de otros ejercicios o dominios.

## 4. Acuerdos y Decisiones Tomadas

- **DEC-04.1:** Utilizar el formato  
  **“Como [rol] quiero [objetivo] para [beneficio]”**  
  para redactar todas las historias de usuario.

- **DEC-04.2:** Utilizar el método **MoSCoW** para priorizar historias de usuario y requisitos.

- **DEC-04.3:** Diferenciar visualmente las prioridades mediante colores, manteniendo siempre una etiqueta textual de prioridad para garantizar la accesibilidad de la documentación.

- **DEC-04.4:** Las historias consideradas prioritarias deberán incluir **pruebas de aceptación** y una **división en tareas de implementación**.

- **DEC-04.5:** Las historias de menor prioridad podrán documentarse mediante una tabla reducida que incluya, como mínimo, el usuario, la historia y su prioridad.

- **DEC-04.6:** Mantener toda la documentación técnica y de análisis en un formato homogéneo en **LaTeX**, facilitando su incorporación posterior a la memoria del proyecto.

- **DEC-04.7:** Revisar la trazabilidad y coherencia de los requisitos antes de incorporarlos definitivamente al Product Backlog del proyecto.
